**โปรเจกต์เป้าหมาย:** `D:\sayari-project`  
**วันที่ตรวจเอกสาร:** 18 ตุลาคม 2026 (Asia/Bangkok)  
**ชนิดไฟล์:** เอกสารงาน + Prompt + Endpoint registry + เครื่องมือเก็บข้อมูล/หลักฐาน + Unit tests ไม่ใช่โปรเจกต์ React สำเร็จรูปที่นำไปทับ source ได้ทันที

## สิ่งที่ยืนยันได้และยังยืนยันไม่ได้

ยืนยันรูปแบบหลักได้จาก source ของ `hakushin-py`: manifest 1 แบบ + index 4 แบบ + detail 4 แบบ + localized item dictionary 1 แบบ รวม **10 URL templates** ไม่ใช่ 10 คำขอจริง และไม่ใช่คำรับรองว่า Nanoka มีแค่ 10 แบบ [C01–C03]

หน้าเว็บ Nanoka มีหมวดอื่น เช่น Monster, Achievements, Shiyu Defense, Hollow Zero และ Version Changelog จึงกำหนดให้ Codex ตรวจเมนู/แท็บ/Network ต่อก่อนลงชื่อว่าครบ [W01–W05]

ในรอบเตรียม ZIP นี้ **ยังไม่ได้รับ JSON จริงจาก CDN Nanoka** การเรียกผ่านเครื่องมือเว็บเข้าถึงไม่ได้ และเครือข่ายของ container มีปัญหา DNS จึงไม่แนบ sample เกมปลอมแทนของจริง ไม่ hardcode เวอร์ชันจากข้อความ search และไม่ได้แก้ `D:\sayari-project` ซึ่งเข้าถึง source จริงไม่ได้จากที่นี่

ตัว collector/publisher มี unit tests ด้วยข้อมูลสังเคราะห์ที่แยกชัดเจน ผลอยู่ใน `evidence/` การผ่าน unit tests ไม่ยืนยันว่า API ออนไลน์, CORS ผ่าน หรือ UI ในโปรเจกต์เสร็จแล้ว

## ขอบเขต “ทั้งหมด” ที่ตั้งไว้

ค่าเริ่มต้น: ข้อมูลสาธารณะทุกหมวดที่ค้นพบ + ทุก record + ทุก field + ทุก locale ที่ตรวจยืนยันของ Live/Latest ณ เวลารัน โดยแสดง Live เป็นค่าเริ่มต้นและ Latest แยกชัดเจน

ประวัติทุกเวอร์ชันเก่าไม่ดาวน์โหลดรวดเดียวโดยปริยาย เพราะจำนวนคำขออาจมาก แต่ต้องแสดงรายการเวอร์ชันจาก manifest และมีวิธี sync เวอร์ชันเก่าอย่างชัดเจน ไม่ซ่อนว่ารุ่นไหนยังไม่ได้โหลด ไม่รวมบัญชีผู้เล่น/UID, API ของเกมอื่น, endpoint ส่วนตัว และการดูดไฟล์ภาพ/เสียงทุกไฟล์ใน CDN

อ้างอิงแบบ `[C01]`, `[M01]`, `[W01]`, `[T01]` ในเอกสารนี้ค้น URL และข้อจำกัดได้ใน `reference/sources.json` เอกสารที่เสนอการออกแบบ Sayari เป็นคำแนะนำของชุดงาน ไม่ใช่คำประกาศของ Nanoka
